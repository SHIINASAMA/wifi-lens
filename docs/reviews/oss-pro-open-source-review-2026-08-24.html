产品商业化与开源治理审查

长期价值、OSS→Pro 转化与 Open Source First

WiFi Lens 的方向是成立的：开源版保留完整、可信的实时诊断能力，Pro 不靠削弱 OSS，而是提供时间线、统计和可解释洞察组成的长期上下文。 当前的主要问题不是“功能不够多”，而是三条链路还没有完全闭合：Analysis 还缺证据到行动和用户验证；转化还缺深度价值演示与可靠反馈；Open Source First 还缺统一事实源和更完整的第三方治理。

执行摘要

无 P0 阻塞 项目已经越过“是否有人愿意使用”的阶段：真实下载、少量付费、Release 后短期放大和弱被动搜索流量都说明方向有市场信号。但收入仍是低样本信号，不能证明 Pro 已经形成稳定、可重复的商业模型。

长期价值业务的技术基座明显好于早期的“页面已存在”状态。Timeline 能回答发生了什么，Statistics 能聚合事件分布并诚实区分覆盖度不足，Insights 已经从统计走向带证据、置信度、适用性和建议的解释层。更重要的是，Insight 可以回到 Timeline 的精确证据，而不是只给一个抽象结论。

当前最大的业务缺口是闭环末端。用户看到证据后，还没有被自然引导到 Network Self-Check、监控 SSID、阈值提醒、导出材料或下一次验证；也没有足够的 opt-in 反馈证明这些洞察缩短了排障时间。因此 Analysis 应继续按 Preview 表达，不应宣传成成熟的根因诊断。

OSS→Pro 转化链路的设计取向正确：入口可见但不打断核心任务，邀请有门槛、冷却和上限，导出成功和诊断完成都是真实价值时刻。短板在于用户第一次看到锁定预览时只能理解“有这个功能”，还不能低成本体验“长期数据如何改变结论”。同时，本地 Guidance 日志无法完整度量外部购买，App Store campaign 也只有单一来源标签。

Open Source First 的基础扎实：Apache 2.0、ChartLens 独立库、贡献政策、安全政策、CI/CodeQL、发布签名公证、五语言应用本地化和无遥测默认值都超过很多早期项目。主要缺口是产品事实漂移、第三方致谢不完整、IEEE 衍生数据的再分发依据需要确认，以及缺少面向使用者和贡献者的公开路线图。

范围与方法

评估范围

  • Timeline、Statistics、Insights 的行为级完成度、状态设计和体验链路。
  • OSS 内的引导触点、生命周期 Guidance、版本矩阵、官网 FAQ、下载页和 App Store campaign URL。
  • 公开仓库治理：许可证、贡献流程、安全政策、CI、CodeQL、发布工作流、ChartLens 边界和本地化。
  • 运营笔记中的商业基线：收入、下载、SEO/ASO、成本策略、反馈目标和发布节奏。

知识边界

本次评估涉及付费版长期功能，因此只在必要范围内检查 Pro 行为。报告只记录行为级结论，不复制私有路径、符号、schema、存储结构、规则阈值或架构内部细节。公开部分可以引用公共源码和文档事实。

限制

  • 本报告是源码、配置、文档、官网内容和运营记录审查，不是真实多网络环境、长周期留存或付费归因实验。
  • 没有重新运行双版本构建与单元测试；本报告新增的是静态 HTML 文档，后续仅执行结构、渲染、空白字符和知识边界检查。
  • 收入、下载和曝光数据来自运营笔记口径，属于低样本早期信号，不应当作稳定增长基线。
  • 合规与许可观察用于降低工程风险，不构成法律意见。

O-01：Analysis 技术基座成立，但用户价值闭环未完成

P1

长期价值 | 高影响 | 高置信度

现状

当前 Analysis 不再只是导航占位。Timeline 提供事件列表、筛选、自定义日期、展开详情和精确证据模式；Statistics 显示事件总量、严重度分布、时间分布、最新显著事件和上一周期比较；Insights 展示确定性发现、网络归属、置信度、适用性、局限和建议，并能跳回对应 Timeline 证据。系统也能区分无数据、无匹配事件、历史太短、覆盖不可用、部分分析和真正无发现。

缺口

这条链路止步于“解释”。用户看到“反复断开”“网关延迟聚集”“漫游频繁”后，还需要决定下一步：立即运行 Network Self-Check、持续监控该 SSID、设置阈值提醒、对比变更前后、生成给 ISP 或家人的说明材料。当前这些动作要么不存在，要么分散在其他页面，没有形成从 Insight 到行动的一体化路径。项目也还没有足够的 opt-in 反馈来验证洞察是否真的缩短排障时间。

影响

用户可能认可界面专业，却仍把 Pro 当作“更多图表”，而不是“下次出问题时能给出证据和行动的工具”。这会限制留存、复购推荐和口碑传播，也会让规则数量继续增长而业务价值难以证明。

判断

在 evidence-to-action 和用户验证建立前，不要增加更多规则类型。先让三条初始规则变得可执行、可反馈、可解释，比扩展到十条低价值规则更有长期收益。

O-02：转化漏斗缺少可靠反馈和外部度量

P1

OSS→Pro 转化 | 商业决策风险 | 高置信度

现状

OSS 在首次欢迎页、侧边栏 Analysis 分组、Timeline / Statistics / Insights 锁定预览、诊断完成后、导出成功横幅和设置中的菜单栏预览都有 Pro 入口。GuidancePolicy 采用三次有意义完成加两个活跃天的门槛、30 天冷却、最多三次自动邀请，并且支持永久关闭。设计避免了打断式营销，也避免漫游完成被滥用为转化时机。

缺口

本地结构化日志能解释邀请为何展示、取消或关闭，但不能证明外部购买来自哪类价值时刻。App Store campaign 当前主要是单一 ct=oss_invite 标签，欢迎页、锁定页和自动邀请共用同一来源。安装检测只能说明 Pro 应用存在，不能说明购买、活跃或满意。项目还缺少稳定的 opt-in 调研来回答：用户为什么购买、为什么停留、为什么忽略邀请、哪些洞察真的有用。

影响

低样本阶段如果只观察月销量，很容易把 Release 峰值误判为增长，或者把无效触点误判为有效。没有反馈闭环时，团队只能在假设之间摇摆，难以判断该优化 ASO、价格、功能密度还是价值演示。

建议
  • 为不同触点分配独立 campaign 标签，至少区分欢迎页、锁定预览、诊断完成和导出成功。
  • 在 Pro 内加入轻量 opt-in 调研：购买原因、最有价值页面、未满足场景和取消原因。
  • 对 Insight 增加“有帮助 / 已行动 / 误导 / 太晚”四态反馈，不采集网络标识。
  • 以周和 Release 窗口观察曝光、点击、下载、激活、购买、退款和反馈，不追求伪精确单笔归因。

O-03：README 版本矩阵在全部语言中落后于官网和应用

P2

产品事实 | 转化准确性 | 高置信度

证据

六个 README 都说 Pro 增加频谱录制、常驻菜单栏和事件时间线；Features 表也只列 Event Timeline 为 Pro only，没有列 Statistics 和 Insights。官网首页、Download 对比表和 FAQ 已经明确列出菜单栏、Timeline、Statistics 和 Insights 四项 Pro 能力。公开 OSS 目标也实际渲染 Timeline、Statistics 和 Insights 的锁定预览。

影响

开发者用户最常读 README，这里却是最低分辨率的版本事实。潜在买家可能低估 Pro 范围；贡献者可能误解 Edition 边界；宣发、App Store metadata 和截图也更容易继续漂移。

建议
  • 建立一个机器可读的产品能力事实源，字段包含能力名、Edition、状态、最低版本、输入来源和限制。
  • 让 README、官网、App Store metadata、截图说明和 release notes 从同一事实源派生。
  • 明确 Preview 与正式能力的区别，不要让“代码存在”变成“成熟卖点”。
  • 发布前用脚本检查六种语言 README 的关键能力行是否一致。

O-04：IEEE 衍生数据库的再分发依据和致谢需要确认

P1

开源合规 | 法律与信任风险 | 中高置信度

现状

应用资源中包含约 4.4 MB 的 MAC vendor 数据库，内含 57,805 条记录，元数据明确说明其派生自 IEEE Registration Authority 公共列表，并保留了四个 IEEE 来源 URL、快照时间和免责声明。设置页也有面向用户的不隶属声明。

缺口

仓库没有统一的 THIRD-PARTY NOTICES 文件，也没有记录 IEEE 数据允许再分发、修改和商业打包的许可依据。早期内部设计曾明确要求在打包公共列表前确认再分发条款；“公开可下载”本身不等同于“可再分发”。Apache 2.0 主许可证不能自动覆盖第三方数据集。

影响

这是 Open Source First 项目最容易失去可信度的类别：不是代码是否开放，而是是否尊重上游数据和依赖。若条款要求署名、更新声明或禁止 redistribution，当前打包方式会造成发布和商业风险。

建议
  • 立即复核 IEEE Registration Authority 当前条款，记录许可依据、快照日期、来源 URL、所需署名和使用限制。
  • 若允许分发，加入完整 THIRD-PARTY NOTICES，并在 README Acknowledgments 指向它。
  • 若不允许或不明确，改为用户触发的 IEEE 下载或手动导入，并把打包快照移出发布目标。
  • 把 Sparkle、swift-log、MCP Swift SDK 及传递依赖纳入同一自动化第三方声明流程。

O-05：Timeline 已越过 MVP，但仍缺专业工作流出口

P2

长期价值体验 | 产品完成度 | 高置信度

已完成

Timeline 已经支持小时分组、事件图标和严重度色彩、文本搜索、事件类型过滤、All / Today / Yesterday / This Week / Custom 日期范围、展开式详情和网络作用域过滤。空态不再只是一个裸列表；查询失败、存储失败、证据缺失、部分证据和周边上下文都有独立表达。Insight 进入证据模式时还能保留周期、事件类型、网络范围和支持事件 ID。

剩余缺口

专业排障通常要把证据带出应用：导出选定事件 CSV/JSON/PDF、复制脱敏摘要、标注重要事件、关联断开与重连、生成时间段报告。当前 Timeline 更适合本机查看，还不适合作为 IT 支持、ISP 沟通或事后复盘的交付物。相关事件的因果关系仍主要由用户阅读列表推导。

建议
  • 先做“选定周期 + 网络范围 + 事件类型”的导出，而不是一次性做全量报表系统。
  • 导出默认脱敏可选标识，允许用户显式选择包含 SSID/BSSID/IP。
  • 把断开、重连和漫游切换在视觉上配对，减少用户手工拼接。
  • 支持复制单条事件摘要和创建书签，方便跨天追踪同一问题。

O-06：Pro 锁定预览缺少“历史数据改变结论”的演示

P2

转化体验 | 价值感知 | 高置信度

现状

OSS 锁定页有骨架、标题、描述、PRO 徽章和 App Store 入口；Guidance 文案把一次诊断或导出的“当前状态”与 Pro 的“随时间变化”对照起来。这个表达诚实，不会误导 OSS 用户。

缺口

新用户在购买前很难体会三个关键差异：间歇性问题如何在几天后才显形；覆盖度缺失为什么必须区分于健康；同一个信号下降在不同网络作用域下会得出不同解释。静态骨架能传达功能存在，不能传达长期上下文的判断力。

建议
  • 为 Timeline / Statistics / Insights 提供“示例数据”模式，明确水印和 Sample Data 标签。
  • 演示一个短故事：第一天正常、第二天出现三次断开、第三天 Insight 给出证据和建议。
  • 在官网加入 15-30 秒录屏，突出从 Insight 回到 Timeline 证据的动作。
  • App Store 截图按“当前诊断 → 长期记录 → 可解释洞察 → 行动”排列，而不是按菜单顺序罗列。

O-07：开源治理缺少第三方声明、公开路线图和能力状态表

P2

Open Source First | 社区资产 | 高置信度

优势

项目已有 Apache 2.0、CONTRIBUTING、SECURITY、Code of Conduct、Swift CI、Web CI、CodeQL、签名公证发布流程、ChartLens 子模块和清晰的 AI 贡献责任。贡献者可用 Pro promo code 致谢的政策也很克制，没有把贡献变成雇佣或承诺。应用无遥测、MCP 默认关闭且绑定 loopback，符合项目的隐私叙事。

缺口

仓库没有 NOTICE 或 THIRD-PARTY NOTICES，也没有公开 roadmap。`docs/TODO.md` 更像工程待办，不适合直接作为使用者路线图；用户看不出哪些能力是正式、Preview、实验或未来方向。贡献者虽然知道提 issue/discussion，但缺少 good first issue、架构地图和可验证的贡献阶梯。

建议
  • 生成并维护 THIRD-PARTY NOTICES，纳入 Swift 包、运行时框架和数据源。
  • 发布一页公开路线图：Now / Next / Later，每项写清 Edition、状态和非承诺日期。
  • 把产品能力矩阵作为事实源，输出到 README、网站和 release checklist。
  • 维护 good first issue 标签和小型贡献路径：文档、本地化、测试、复现报告、ChartLens demo。

O-08：发布前校验顺序仍有滞后风险

P3

发布卫生 | 工程效率 | 中高置信度

证据

Release workflow 在签名、导出、Sparkle entitlements 检查、DMG、公证和 staple 之后才读取配置并比较 tag 与 marketing version。失败会阻止发布，但发生在大量耗时步骤之后。另外，本次审查所在本地 master 落后远端四个提交，差异目前集中在 CodeQL action 和 Astro 依赖更新。

影响

这不是用户可见缺陷，但会让一次简单配置错误消耗大量 CI 时间，也会提高 release branch 与远端漂移的风险。

建议
  • 把 tag、marketing version、build number 和 submodule 状态检查移到证书导入之前。
  • release job 开始时执行 `git status --porcelain`、远端同步和 ChartLens pinned commit 校验。
  • 为 release workflow 增加 dry-run 或 workflow_dispatch 冒烟路径。

长期价值完成度与体验

长期价值的定义应当很窄：在下一次 Wi-Fi 问题发生时，用本机保存的历史证据帮助用户更快缩小范围、确认是否复发，并采取具体行动。它不是保存尽可能多的日志，也不是给每个现象都起一个因果名称。

能力完成度

模块已完成主要缺口完成度判断
Timeline 事件浏览、筛选、搜索、自定义日期、详情展开、证据模式、错误与部分证据状态。 事件级导出、标注、事件关联、复制摘要、跨天追踪仍然薄弱。 可用 Preview，约 70%。
Statistics 24 小时 / 7 天 / 30 天周期、网络作用域、覆盖率、事件分布、严重度、显著区间、上一周期比较。 按网络的横向比较、变化解释、异常前后对比和行动入口不足。 基础成立，约 72%。
Insights 确定性规则、严重度、置信度、适用性、局限性、证据计数、时间范围、建议和回跳 Timeline。 缺少行动按钮、用户反馈、效果指标和对排障时间的证明。 方向正确，约 60%。
冷启动与采集 无历史不会被表述为零活动或健康；Pro 引导强调录制、时间线和分析。 用户不清楚要积累多久、当前是否充分记录、何时值得回来查看。 最大体验断层，约 50%。
数据控制 本地存储、清除入口、隐私安全反馈邮件和无遥测默认。 缺少统一 Data & Diagnostics 面板、保留策略和磁盘占用说明。 基础可控，约 65%。

体验上已经正确的决定

  • 不确定性是一等公民。无数据、无匹配事件、历史不足、覆盖缺失和部分分析没有混成一个“正常”。这对诊断工具非常关键。
  • 证据可以回溯。Insight 不只给标题和建议，而是携带支持事件并回到 Timeline；这把“AI 式结论”拉回可验证证据。
  • 共享分析选择。周期和网络作用域在 Statistics 与 Insights 间保持一致，降低用户在不同页面得出互相矛盾结论的风险。
  • 非阻塞引导。Pro 邀请放在真实价值动作之后，有冷却、上限和永久关闭；这与 OSS 完整性的定位一致。
  • 隐私边界克制。反馈邮件只含应用版本、系统版本和 edition，不自动附带 SSID、BSSID 或诊断结果。

下一个价值跃迁

下一步应实现最小 evidence-to-action 循环：

  1. Insight 卡片提供“Run Network Self-Check”“Monitor this network”“Export evidence”“Mark as helpful/misleading”。
  2. 用户选择监控后，显示当前采集状态、预计最少积累窗口和历史充足后的提醒条件。
  3. 阈值提醒先覆盖 RSSI、网关延迟和反复断开，不做复杂预测。
  4. 导出生成可分享但默认脱敏的摘要，连接 ISP、家人、同事或 IT support 场景。
  5. 用 opt-in 反馈和留存判断是否扩展规则目录。
发布语言应保持“本地历史证据”和“可解释模式”，暂缓“根因分析”或“网络健康管理平台”这类说法。前者已被实现支撑，后者还没有被用户结果验证。

OSS→Pro 转化链路

当前策略不是把 OSS 做成残缺试用版，而是在用户解决当前问题后展示长期上下文的价值。这个定位值得坚持；人为削弱 OSS 会伤害开源传播和信任，也会与“完整实时诊断工具”的事实冲突。

漏斗判断

  1. 发现：GitHub Release、官网 SEO、ASO 和目录站已经产生被动曝光；运营笔记记录 1.5.1 发布后约 2-3 小时约 30 次下载，以及每日约 20 次量级的搜索曝光。这说明分发开始有积累效应，但仍受 Release 峰值影响。
  2. 理解：官网能说清 OSS 与 Pro 差异，README 不能；应用内锁定页能说清功能名，不能充分演示长期价值。
  3. 激活：OSS 的扫描、信道分析、Network Self-Check 和导出足以完成第一次任务，这是信任资产，但也意味着一次性问题用户可能自然流失。
  4. 付费动机：真实动机应从“多三个页面”转为“下次间歇性故障时有证据”。当前文案已指向这一点，但演示不够。
  5. 留存与验证：缺少 monitored SSID、提醒、周期报告和 insight 有用性反馈，长期价值还主要靠用户自己搭建流程。

商业基线

截至 2026-08-11，累计收入接近 60 美元；此前约一个半月至两个月累计只有个位数付费用户。8 月上旬销量强于早期，但样本仍小。成本策略调整后，盈亏平衡门槛降至约每月 1.5 份 Pro。这个数字有助于维持开发，但不能证明模型稳定；更重要的是跨月销量、退款、使用频率、购买原因和主动反馈。

转化建议

  • 先改价值表达，再做广告。用 Sample Data、截图和录屏证明“历史如何改变结论”，比扩大曝光更能改善低样本漏斗。
  • 把导出做成转化资产。免费导出当前快照，Pro 导出跨周期证据；两者都应默认脱敏并可分享。
  • 建立反馈闭环。购买原因、未满足原因、insight 是否有用、是否缩短排障时间，比单纯销量更能指导下一版本。
  • 拆分 campaign。欢迎页、锁定页、诊断完成和导出成功分别标记，才能判断哪个价值时刻真正推动购买。
  • 优化 ASO 第一眼。当前问题是点击意愿弱，不是完全没有曝光；首图和前两张截图应呈现问题、证据和结论。
  • 不要引入打断式弹窗。现有门槛、冷却和关闭机制应保留；转化不足应通过价值密度解决。

Open Source First 评估

Open Source First 不等于“所有东西都必须免费”，也不等于私有 Pro 不能存在。它要求公开部分可构建、可审计、可贡献、可信任，并且商业边界诚实。WiFi Lens 在多数维度上做到了这一点。

维度评价

维度评价依据
源码开放良好OSS 核心实时诊断完整开源；ChartLens 作为独立库开放；Pro 只保留额外长期工作流。
许可证需完善主项目和 ChartLens 为 Apache 2.0，但第三方数据与依赖声明不完整。
贡献体验良好CONTRIBUTING 明确范围、测试、PR、AI 责任和 promo code 致谢边界。
安全治理良好SECURITY 定义私有报告、响应目标、范围、披露和安全港。
自动化质量良好Swift CI 运行 OSS build/unit tests；Web CI 执行 check/build；CodeQL 覆盖 Swift 和 interpreted languages。
发布供应链可改进DMG 签名、公证、staple 和 Sparkle entitlements isolation 已具备，但版本校验偏晚。
产品透明度需完善官网事实较新，README 全语言漂移；缺少公开 roadmap 和状态矩阵。
隐私与本地优先良好应用无遥测；MCP 默认关闭并绑定 loopback；扫描数据留在 Mac。
社区资产早期issue/discussion/open source 内容存在，但缺少公开路线图和结构化贡献阶梯。

最强资产

  • 完整 OSS 是获客引擎。用户可以先解决实际问题，不需要为了基本诊断付费。
  • ChartLens 是可复用的技术信誉资产。它既支撑产品，又能吸引图表/SwiftUI 开发者，形成与主 App 不同的传播面。
  • 本地优先与无遥测是高信任差异点。网络数据高度敏感，这一原则应继续约束所有新功能。
  • 治理文件质量高。CONTRIBUTING 和 SECURITY 不是模板化文件，能减少低质量 PR 和不当披露。
  • 多语言不只是翻译。应用五种语言、README 六种语言和官网多语言共同扩大了自然发现面。

Open Source First 的下一步

  1. 把“产品事实源”当作开源基础设施，而不是营销附件。
  2. 补齐 THIRD-PARTY NOTICES 和数据来源审计记录。
  3. 发布公开 roadmap，明确 Now / Next / Later 与 Preview 边界。
  4. 为贡献者提供小型、可验证入口：本地化回归、截图矩阵、文档修正、ChartLens 示例。
  5. 把 release checklist 公开化：构建、测试、i18n、知识边界、第三方声明、隐私文案、签名公证。

行动顺序

下一次发布门槛

  • 统一 README 六种语言的能力矩阵，加入 Menu Bar、Timeline、Statistics 和 Insights。
  • 确认 IEEE 数据再分发依据；根据结果补 THIRD-PARTY NOTICES 或移除打包快照。
  • 为 Insight 增加最小反馈：有帮助 / 已行动 / 误导 / 太晚。
  • 为不同 Pro 触点拆分 App Store campaign 标签。
  • 发布页明确 Analysis 仍为 Preview，不宣称成熟根因诊断。

30 天内

  • 上线 Sample Data 模式，演示从 Insight 回到 Timeline 证据的路径。
  • 实现 monitored SSID 的采集状态页：正在记录、观测时长、覆盖缺口和预计可用时间。
  • 为 RSSI、网关延迟和反复断开提供保守阈值提醒。
  • 实现 Timeline 选定范围的脱敏导出。
  • 建立购买原因和流失原因的 opt-in 调研。

90 天内

  • 用留存、insight 反馈、排障时间和跨月销量判断是否扩展规则。
  • 发布公开 roadmap 和能力状态矩阵。
  • 补齐第三方声明自动化与 release checklist。
  • 建立浅色/深色、更大文本、五种语言、无权限、无 Wi-Fi、空历史和部分历史的视觉回归矩阵。
  • 把 release tag/version/submodule 校验移动到昂贵发布步骤之前。

成功指标

  • OSS Release 后 24 小时 / 7 天下载曲线逐次抬高。
  • 官网和 App Store 曝光到产品页、下载、激活的相对转化提升。
  • Pro 7 天和 30 天留存，尤其是 Timeline/Statistics/Insights 回访率。
  • Insight 被标记为“已行动”的比例和被标记为误导的比例下降。
  • 从首次症状到用户确认原因或排除假设的中位时间缩短。
  • 跨月新增购买、退款率和可归类购买原因数量增加。
